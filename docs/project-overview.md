# 项目整体说明

## 这是什么

「相册整理」（PhotoOrganizer）是一个**自用**的 iPhone 相册清理工具。它把相册读一遍，算出每张照片的特征，然后按"你可能想删"的角度分成几堆，让用户自己挑。

它不接管相册，不做云端同步，不提供"一键智能清理"。所有判断都发生在手机上，删不删由用户点。

## 给谁用

- 主要用户：项目作者本人（Eddie），相册规模约 **2.1 万张**，长期只增不减。
- 不是给大众用的产品：没有账号、没有引导流程、没有多语言，UI 文案是口语化的中文。
- 因为是自己用，**敢于给"建议"而不是给"保证"**：宁可提示"这张可能有 13% 概率想删"，也不假装准确。

## 边界

**做：**

| 能力 | 口径 |
|---|---|
| 完全重复 | 原图字节完全一致（SHA-256 + 尺寸） |
| 相似 | dHash 汉明距离 ≤ 8，字节不同 |
| 模糊 | 拉普拉斯方差（对比度拉伸后）显著低于本相册中位数 |
| 截图 | 系统标记 + 亮度 / 边缘密度辅助 |
| 大文件 | 按体积排序，用于空间看板 |
| 内容分类 | Vision 场景分类 + OCR，输出发票票据 / 文档 / 截图 / 人物 / 美食 / 风景 / 宠物 / 其他 |
| 发票识别 | 二维码优先，其次 OCR 关键词 |
| 处置 | 选中删除、逐张过（滑动标记）、视频转 720p、导出文本清单 |

**不做：**

- 不做云、不做登录、不上传任何一张图（这是硬承诺，不是"暂时没做"）。
- 不做自动清理 / 定时清理 / 后台扫描。扫描必须由用户点"开始扫描"，且必须在前台。
- 不做"相似度百分比"这类伪精确指标：只给同组关系，不给数值。
- 不支持 iPad、横屏、深色模式。
- 不追求识别准确率到商用级别；错判靠"手动排除"兜底。

## 版本演进（按能力，不按营销版本号）

| 阶段 | 关键变化 | 遗留问题 |
|---|---|---|
| 首版 | 重复 / 相似 / 模糊 / 截图 四类扫描，只读不删 | 大库扫得慢，结果页信息密度低 |
| 交互版 | 点按选中、1/2/3 列布局、模糊灵敏度三档 + 手动排除、Tinder 式逐张过 | 模糊判定在低对比场景误伤 |
| 自动化版 | Maestro 8 条云端用例、`_ci_check.py` 一键取回结论 | 模拟器授权顺序反复踩坑 |
| **1.4 (17)** | **两阶段扫描**（先出结果，内容识别后台补齐）+ 发票二维码识别 + 空间看板 + 视频压缩 | 全库扫描仍要约 13 分钟（见 `TODO.md` P0） |

## 几个关键取舍（不是随手决定的）

**为什么全部本地算？**
用户的核心顾虑是照片隐私。一旦引入上传，"整理工具"就变成"把相册交给别人"。所以宁可慢、宁可识别率低，也不加网络。

**为什么扫描分两段出货？**
21482 张的库，完整跑一遍特征 + 内容识别要十几分钟。特征部分一分钟级就能出结果，内容识别（Vision）贵一个数量级。两段出货让用户一分钟就能开始清理，发票和分类在结果页后台补进来。代价是缩略图要取两次。

**为什么"完全重复"要用 SHA-256 而不是只看 dHash？**
dHash 相同只说明"看起来一样"，可能是两张不同时刻拍的同一场景。删照片是不可逆操作（30 天后），必须字节级证据才敢标"重复"。

**为什么相似分组用星型聚类而不是并查集？**
传递合并会让 A≈B、B≈C 把 A 和 C 并进一组，而 A 和 C 可能差很远。星型聚类只跟种子比，组内一致性更高，代价是同一批连拍可能被切成两组——这个代价可以接受。

**为什么固定浅色？**
界面是白卡片 + 蓝按钮的"工具感"风格，深色模式会让缩略图与卡片对比失衡。`preferredColorScheme(.light)` 是明确决定，不是没做。

## 成功标准

1. 2 万张的库，点"开始扫描"后 **90 秒内**能看到可操作的结果页。
2. 建议清理里点开的照片，**七成以上**用户会认同"确实可以删"。
3. 任何一次删除都能在「最近删除」里找回，**没有不可逆路径**。
4. 扫描过程中不闪退（历史上有过 jetsam，见 `architecture.md`）。
